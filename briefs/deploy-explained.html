The 4 stops your code travels

Think of it like a restaurant: you cook → publish the recipe → the kitchen cooks it → the sign tells customers where to walk in.

💻
Stop 1 · Your computer

Local commits You are here

12 commits from this session live ONLY on your machine right now. GitHub & Vercel haven't seen them yet — so the live preview still shows the old code.

🐙
Stop 2 · GitHub

The shared recipe book

When you push your commits to the master branch on GitHub, your work becomes the official recipe. Nothing is deployed yet — it's just saved & shared.

▲
Stop 3 · Vercel

The kitchen (auto-cooks)

Vercel is watching the master branch. The moment new code lands there, it automatically builds & deploys (~2 min) to pmrfp.vercel.app. You don't click anything.

🌐
Stop 4 · DNS (Hostinger)

The address sign

Last step: point pmrfp.com at the Vercel kitchen. Only do this after Stops 1–3 are done & verified — otherwise the sign points customers at an empty/old kitchen.

✅ Your instinct is right: deploy (Stops 1→3) before DNS (Stop 4). Pointing the domain at Vercel before the new code is deployed just shows visitors the old site.

So what does "Create PR" do?

A Pull Request (PR) is a "ready to publish?" review note. It proposes merging one branch's code into master.

• Opening a PR = nothing goes live. It just shows the changes for review.
• Merging the PR into master = the code lands on GitHub → Vercel auto-deploys.
So a PR is just the doorway to Stops 2→3. Merging it is what actually ships.
⚠️ Careful — the "Create PR" you're seeing is the wrong branch. GitHub is offering a PR for your old design branch, not this session's work. If you merge that, you'd pull in stale design-branch code. Don't merge it. Our 12 commits are on master locally and need to be pushed, not PR'd from design.
