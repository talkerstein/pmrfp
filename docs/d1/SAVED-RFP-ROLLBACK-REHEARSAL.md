# Saved-list rollback rehearsal

Rolling back after a new backend accepts writes requires transferring those writes back to the old backend. This rehearsal covers only the five persisted fields of `saved_rfps`. It does not authorize real D1 writes or provide a production rollback tool.

The sample SQLite triggers capture before/after images in the same transaction as each insert, deletion or actual update. A duplicate save or failed transaction leaves no new event. On November 9 a disposable set of tables in the existing isolated D1 journal canary verified this behavior using synthetic rows. Native rows and journal entries from a batch containing an invalid foreign key both rolled back. A local replay from the initial rows matched all fields of the native final rows. The canary tables and triggers were removed and their absence verified.

From the worktree root, run `python3 -m unittest discover -s test/d1 -p test_saved_rfp_rollback.py` for local capture and replay. Run `python3 test/d1/rehearse_saved_rfp_postgres.py` with PostgreSQL CLI binaries installed to verify the PostgreSQL half. It creates a disposable PostgreSQL instance listening only on a private temporary socket and uses the application's real saved-list column types and constraints with synthetic parents and rows. The target locks the table, compares each before image, verifies the full final table against the frozen expected readback, and commits only on an exact match. Conflicts, missing events, or a final-state mismatch leave the target unchanged. The PostgreSQL script refuses a database with any other name.

Before using this approach at cutover, both databases need an agreed frozen baseline, an authenticated and complete journal checkpoint, and a separate, least-privilege production replay path. Related account, organization and RFP changes must replay in order with their saved lists, including cascades. Capture, fencing, backups, and exact replay are still required for other writes, including Auth, files, jobs and payment events. Never install these rehearsal triggers on the current Source-to-D1 replica: they would also capture migration writes.
