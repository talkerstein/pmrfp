# Source change-capture proposal — October 31

**Review only. Not installed in Supabase. Production remains authoritative there.**

The next writable-preview dependency is durable tracking of source changes,
including account/membership changes and deletes. The current complete-snapshot
and reversible-journal path is verified, but it is not continuous change capture.

## Proposed source change

`d1/change-capture-proposal-2026-10-31.sql` is generated by
`scripts/d1/change_capture.py`. Its default approval guard aborts before creating
anything. After explicit approval it would atomically:

- Check the exact 108-table/primary-key inventory, existing reader flags/expiry,
  SELECT grants, absence of application write privileges and inherited public
  definer execution boundaries.
- Create a private `d1_migration` schema, registration table and outbox with RLS,
  no PUBLIC access and no anon/authenticated/service-role schema access.
- Add row and TRUNCATE capture triggers to the 108 audited public tables.
  Events contain table name, operation, primary key, transaction ID and time;
  they do not copy full rows, message bodies, emails or Auth password hashes.
- Give the existing expiring reader SELECT on those two private tables and
  EXECUTE on one bounded acknowledgement function. This function updates only
  acknowledgement metadata for 1–500 existing receipt IDs. It retains receipts,
  is idempotent and stops accepting acknowledgements at November 5, 10:00 UTC.
  The reader login expiry, credentials and application-table permissions remain
  unchanged.

Installation does not rewrite existing customer rows, application functions,
policies or grants. It does add metadata writes to subsequent source changes.
Capture remains active until detached. If recording an event fails, the source
transaction fails too, preserving consistency; this couples source availability
to the queue. Setup acquires all audited table locks with NOWAIT, refusing to wait behind
active writers. Trigger attachment/removal each runs as one bounded statement;
30-second statement and (where supported) transaction timeouts limit setup, with
a five-second fallback lock timeout. New writes can wait briefly until commit. Source production performance is unmeasured. The local fixture records
500 keys from 500 large-body inserts using under 256 KB of queue-row metadata;
that is correctness/size evidence, not a production capacity guarantee.

## Bootstrap and acknowledgement boundary

After an approved installation, `migrate.py export --capture-outbox` captures all
visible unacknowledged IDs as strings in the same repeatable-read transaction as
the full source snapshot. It refuses an unrecognized queue schema or more than
75,000 pending events. Default exports remain unchanged.

`scripts/d1/acknowledge_capture.py` defaults to a local plan. Its explicit
`--commit-ack` path requires the pinned source reader/pooler with verified TLS,
the approved rebuild's exact source-parent/policy hashes, preservation of every
authoritative field, and complete native D1 schema/field/FK validation against
the pinned copied-data preview. Only then does it acknowledge the captured IDs
in batches of 500. It never changes source application tables.

Never use a maximum-ID watermark: sequence IDs can commit out of order and
rollbacks leave gaps. Poll **all unacknowledged** events, and acknowledge only
IDs observed in the same source transaction as the copied data. New/late events
remain pending, even when their IDs are lower than an acknowledged ID. Native
reversal tests must finish before acknowledgement; reversing an acknowledged
checkpoint invalidates the incremental baseline and requires a new full source
bootstrap.

Row-key capture and a verified full-bootstrap acknowledgement are prepared.
Low-egress current-row extraction, continuous replay scheduling, transaction
coalescing, durable consumer receipts and freshness-gated application writes
remain unimplemented. Installing the queue does not complete those gates.
Future source schema changes require another audit and trigger registration.

## Recovery and verification

`d1/change-capture-detach-2026-10-31.sql` checks the schema marker, removes only
these capture triggers and revokes the newly added reader permissions. It
preserves customer data and all queued events/receipts. The schema is retained;
reinstallation requires separate review.

Local PGlite checks exercise approval/schema guards, unchanged reader expiry and
settings, insert/update/delete/no-op/composite-key/TRUNCATE capture, transaction
rollback, existing RLS, private-schema isolation, denied customer writes and
trigger attachment, bounded/idempotent acknowledgement, late lower IDs and
non-destructive detach. Offline tests also reject invalid receipt IDs, unsafe
source connections, unrelated rebuilt candidates and native verification failure
before any acknowledgement call. No source installation or live acknowledgement
has occurred.
